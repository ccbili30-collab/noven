# 世界星座工作台产品发现

## 讨论背景

本轮使用 Growth World Pro 的真实物化关系制作了可丢弃 Web Prototype（网页原型）。原型最初把 `causes` 关系中的事实节点直接投影为三维“因果球”。用户随后纠正：其预期主语不是事实因果节点，而是作品文件及其引用关系。

该纠正与当前 `CSK-601` 至 `CSK-606` 所定义的纯 `/causality` 关系网存在产品层级差异，不能在未定级前静默覆盖现有规格。

## 用户纠正后的产品含义

1. 外层天球由十二个世界层级构成十二个星座。
2. 星座的成员是作品文件，而不是从正文抽取的单句事实。
3. 作品文件属于某个星座；作品内部再展开为多颗事实星辰。
4. 作品之间适合显示引用、采用、支持或其他真实作品关系；外层不要求所有关系都是因果。
5. 星座是空间聚合体，星座之间可以稀疏。
6. 跨星座作品关系显示为星空中的弧形航道：靠近或进入相关星座时明显变亮，缩回天球后仍保留微弱可见的空间痕迹。
7. 进入单个星座后，应能够清晰阅读作品之间的关系；进入作品后，再阅读作品内部事实及因果。
8. 作品与事实必须能够进入对应真实项目文本，不能只显示一条关系摘要。

## 当前原型为什么不符合

- 原型只选择 `type === "causes"` 的 393 条边，忽略作品级 `adopts`、`supports` 等关系。
- 631 个显示节点都是参与因果的对象或事实，作品文件没有成为一等节点。
- 节点详情虽然包含 `path`，当前浏览器原型只将其显示为普通文本，没有工作台文件导航合同。
- 全图把天球概览与局部因果阅读放在同一三维尺度，导致节点难点、方向难辨和关系说明脱离正文。

## 真实项目数据对新结构的支持

对本轮真实物化关系和作品文件的只读统计得到：

- 完整原型数据包含十二层、193 个作品文件和 1,602 个作品内部事实节点。
- 十二层每层包含约 15 至 17 个作品文件，适合直接形成十二个星座聚合体，不需要重要性筛选。
- 按作品折叠和去重后包含 1,104 条作品关系，其中 1,070 条为 `adopts`、34 条为 `causes`；作品引用是外层星图更主要的真实关系。
- 作品内部保留 1,355 条事实关系，不将它们提前混入天球总览。
- 作品级 `adopts` 覆盖十二层之间全部 66 个有向层级组合。若同时绘制所有星座对航道，仍会形成不可读的完整网。
- 因此天球缩放态必须采用多尺度聚合或共享航道束：总览只留下弱可见的聚合轨迹；进入星座后再展开该星座的作品级航道；进入作品后才展开具体引用端点和事实关系。

## 建议的三层信息结构

```text
十二层天球
  → 星座：世界层级
    → 作品：真实 Markdown、图片或其他项目文件
      → 事实星辰：作品内部对象、事件、规则、论述或事实
```

关系同样分层：

- 星座间：聚合后的跨层作品航道，只表达存在和规模，不伪装具体因果。
- 星座内作品间：引用、采用、支持及明确因果分别编码并可筛选。
- 作品内事实间：因果、包含、顺序或其他事实关系，必须保持类型区分。

跨星座作品边不应参与星座中心的强物理吸引，否则会破坏十二聚合体。它们只影响航道展示；进入相关星座或作品时再展开具体端点。

## 与现有 `/causality` 规格的关系

现有 `CSK-601` 至 `CSK-606` 仍要求因果边与文件引用、目录包含和普通关联明确区分。新发现没有授权把引用关系改名为因果。

当前存在两个合理产品路由，尚需用户确认：

1. 世界星座工作台成为上层通用作品导航；`/causality` 只负责其中的因果筛选与作品内部因果视图。
2. `/causality` 扩展为多关系世界星图，但产品名称、规格和验收必须相应修订，且默认视图不能把普通关系伪装成因果。

在该路由决定前，不修改生产 Skill、公开协议、工作台注册合同或持久数据模型。

## 2026-08-06 可操作原型验证

当前可丢弃原型已按三层结构重新构建，并完成一轮 Chromium 自动交互验证：

- 天球显示十二个层级星座，作品恒星组成星座轮廓，跨层作品关系聚合为弱可见弧形航道。
- 进入“宇宙、自然与地理”后显示 17 部作品及通往其他层级的聚合星门。
- 进入《九河盆地》后，图中左侧显示它引用的作品、右侧显示引用它的作品，中心周围显示 8 个作品内部事实；侧栏保留全部 4 条引用和 10 条被引用作品入口。
- “打开真实作品”读取并渲染真实 Markdown，本次读取文本为 4,712 个可见字符。
- 作品到星座、星座到天球的返回链通过；页面加载、搜索、下钻、文件预览过程中没有 Page Error（页面错误）、Console Error（控制台错误）或资源请求失败。

该结果只证明 Prototype（原型）的信息结构和真实文件读取可行，不证明生产工作台导航、持久化、性能、键盘可访问性或正式 Skill 已实现。是否以该结构替换或包裹 `/causality` 仍由用户看过原型后决定。

## 第一版视觉被否决及第二版修正

用户否决了第一版天球视觉，但没有否决三层信息结构。被否决的具体原因是：每层使用中心节点向作品放射，外观成为“蒲公英”而非星座；大量同构曲线形成僵硬铁丝球；数千颗不可点击背景星与作品节点使用相近视觉语言，产生虚假可点击暗示。

第二版原型据此只替换绘制语义：

- 去除天球和星座内部的层级中心节点，15 至 17 个作品恒星直接组成一条不规则主干及三条短分支。
- 天球中的层名改为无中心光点的可点击文字标签；点击任一作品恒星同样先进入其所属星座。
- 跨层关系按无向层对聚合，默认只保留十条最强航道的极弱痕迹；悬停相关星座后才提高对应航道亮度。
- 航道从同构二次曲线改为带固定随机侧向偏移的三次空间曲线，并用柔和外晕和细芯两层表现。
- 背景星从 3,760 颗高亮点降为 1,020 颗低亮细尘，不使用作品恒星的光晕尺度，也不提供悬停或点击反馈。

第二版仍是待用户目视判断的 Prototype，不表示上述绘制语义已成为产品规格。

## 艺术星空背景探索

用户接受了一张生成式现代艺术星图作为美术方向，并进一步要求保留可旋转伪三维天球。原型新增两种可直接切换的背景实验：

- `程序星空`：球面 Shader 生成深蓝银河、暗云和远景雾气，三层不可交互 Points 生成针尖背景星，另加极淡天球经纬网。该方案天然无贴图接缝。
- `全景贴图`：生成式 2:1 星空图只提供银河云气，细星经本地中值滤波移除后仍由三维 Points 提供；避免纹理放大后形成模糊雪点。

全景图曾请求 `3840×1920`，但当前图片 Provider 实际返回 `1774×887`；因此不能把它记录为 4K 证据。纯贴图版本在球面放大后星点明显模糊，已被原型内的混合方案取代。当前两版都只使用背景 Mesh 或 Points，不参与图节点命中；可交互作品恒星统一改为珍珠白，星座线统一为银灰色，淡金色只保留给跨星座航道和选择强调。

该实验仍未决定正式背景路线，也没有修改生产 Renderer 或 `/causality` Skill。

## 原型下一步边界

允许继续制作明确标记的可丢弃 Web Prototype，用真实文件路径与现有关系数据验证：十二星座聚合、作品级节点、跨星座弧形航道、星座内关系阅读和作品内事实展开。原型中的文件跳转若未接入真实工作台，只能标注为 Prototype，不能称为 Live。

## 统一球面与关系聚焦修正

用户确认不再允许单独拖动任何作品节点，并要求恢复第一版中“点击后立即理解关系”的直观性，同时保留艺术全景背景和伪三维天球。

当前可丢弃原型据此调整为：

- `3d-force-graph` 关闭 `enableNodeDrag`；拖动只旋转整颗天球，滚轮只缩放视图。
- 十二层、193 部作品和星座轮廓统一固定在半径一致的完整球面上；半透明球壳和低亮经纬线提供连续球体轮廓。
- 未选择作品时，仅显示星座轮廓和少量低亮聚合航道，避免将全部 1,104 条作品关系同时铺开。
- 第一次点击作品不再直接进入星座或正文，而是在天球中聚焦该作品：压暗无关作品，沿球面显示其真实引用和被引用关系，并使用箭头表达方向。
- 右侧详情继续显示关系说明；用户明确点击“打开真实作品”后才进入只读 Markdown 预览。
- 自动浏览器验收通过搜索选择《九河盆地》，确认聚焦状态显示 4 条引用和 10 条被引用关系；点击打开后读取 4,712 个可见字符。

本轮只确认原型交互方向。曲线密度、远端关系在球面背侧的表达、正式工作台文件导航和生产性能仍未定级，不得从该原型推断为已完成能力。

## 用户对“小因果层”的再次纠正

用户指出，作品内部的事实星辰和小因果线不应只在进入单篇作品后才存在。大量小事实、小因果和星尘本身应共同构成世界天球的视觉密度，使天球在未选择作品时已经显得饱满，并允许一个作品节点通过多条关系连接到大量内容。

该纠正意味着原型当前把 `1,602` 个事实节点和 `1,355` 条事实关系完全隐藏在作品下钻视图中的做法不符合预期。背景星尘也不能承担事实星辰的语义，因为它们没有真实来源、关系或选择反馈。

用户确认采用分级命中：天球总览显示全部真实事实与关系，但事实星辰不参与点击；聚焦所属作品后，只有该作品的事实节点开放点击。

当前可丢弃原型已据此接入全部 `1,602` 个事实节点、`1,355` 条事实关系及作品到事实的弱归属纤维。事实关系按已登记类型着色，归属纤维保持低亮银蓝，避免把结构归属伪装成因果。聚焦《九河盆地》后，其 8 个事实节点成为可点击节点，其余事实网络退暗；自动浏览器流程确认事实入口能够打开对应真实 Markdown，本次仍读取 4,712 个可见字符。

该结果只验证 Prototype（原型）中的视觉密度、分级命中和真实文件预览路径，不证明生产 Renderer 的 1,602 节点性能、正式工作台导航或 `/causality` Skill 已实现。

用户随后否决了事实关系挤压成短小锐角线团的布局，要求关系在球面上舒展开并明显增大分支夹角。由于度数超过 3 的节点在二维局部不可能让所有入射边两两保持 120°，原型没有伪造这一几何保证，而是采用关系感知的视觉等价方案：扩大十二星座球面占地；以真实事实邻接关系决定局部排列；通过节点排斥与边长约束展开事实群；将事实关系从直线段改为带确定性侧向间距的球面柔弧；进一步降低结构归属线亮度。该变化仍待用户目视决定是否成为正式布局规则。

用户进一步澄清，事实节点的位置应由布局负责舒展，但事实节点之间的小关系本身应保持直接直线，不能通过弯曲线补偿布局。该澄清废止上一段中的“小关系改为球面柔弧”；当前原型保留关系感知布局与节点排斥，将事实关系恢复为端点间直线。作品级跨星座航道仍为长弧，避免穿越球心；该区分仍只属于待验收原型。

用户目视发现，即使单篇作品内部已经舒展，不同作品的事实群仍会互相插入并卷成一团。代码核查确认旧布局的作品平均间距约为单个事实群半径，而布局排斥只在单篇作品内部生效，未处理作品领地间碰撞。

当前原型改为作品领地布局：每层先以确定性最远点采样分配 15 至 17 个作品位置；按最近作品距离计算各自事实领地半径；事实布局被硬约束在所属领地内；作品骨架由二维最小生成树生成，以避免旧主干造成不必要交叉。事实关系继续使用端点直线。自动截图冷启动复测约 3.1 秒，未发现本轮布局计算造成持续 20 秒级加载；该数字只属于无头 Chromium 原型环境，不是生产性能证据。

用户进一步要求将天球从“大小星点共同发光”改成主节点与关系织网：事实节点不再显示点，只保留事实关系线；只有作品主节点发光；作品主节点之间必须有更清晰的关系线；事实线作为次级网络但仍清晰可见；大部分作品航道允许使用穿过球体内部的直线；主节点和整体球面占比可以扩大，以提高视觉密度。

该要求与此前“聚焦作品后事实星辰开放点击”存在交互冲突。不可见事实节点不能保留隐形命中区，否则会造成无法解释的误触。待用户确认的建议是：事实正文只从右侧事实列表进入；球面只显示事实关系线，不再直接点击事实节点。

用户确认取消事实节点的球面直接点击，事实正文统一从右侧列表进入。当前原型已移除全部事实点及其球面命中对象；193 个作品节点成为唯一发光主节点并扩大；全部 1,104 条作品关系以直线弦穿过球体；1,355 条事实关系作为次级领地网络保留；作品骨架继续提供更强的星座轮廓。全局作品关系经亮度分层后保留全部边但避免整体过曝，聚焦作品时只显示其相关作品直线并增强亮度。

自动浏览器流程再次验证《九河盆地》聚焦后右侧存在 8 个事实入口，点击事实入口可打开 4,712 个可见字符的真实 Markdown。该结果仍只属于 Prototype，不是生产 Renderer、正式工作台导航或 Skill 完成证据。

用户继续要求作品节点像足球面板一样覆盖整颗球，而不是以十二个局部星团贴在球面。当前原型据此用正二十面体的 12 个顶点建立十二层中心，将 12,000 个均匀球面候选点按最近中心划入球面 Voronoi（泰森）领地，再在每个领地内以最远点采样放置该层的 15 至 17 个作品。193 个作品因此覆盖完整球面；每层作品骨架在三维位置上使用最小生成树；球壳增加低亮正十二面体边界作为十二个近似五边形面板提示。

本轮无头 Chromium 总览截图冷启动约 3.9 秒，显示作品节点已覆盖当前可见球面且作品关系直线贯穿内部。该耗时和截图只验证可丢弃原型，不构成生产性能、可访问性或正式视觉验收。

## 总览直线骨架与按需关系聚焦

用户再次区分“星座骨架”与“作品关系”：作品节点之间的星座骨架不得为了贴合球面变成圆弧，而应直接连接两个端点；1,104 条真实作品关系也不得在总览中常驻并贯穿球体，只在用户选中具体作品后按需出现。该纠正废止上文“总览保留全部作品关系”和“作品级跨星座航道仍为长弧”的原型描述。

当前原型已经调整为：

- 十二层星座骨架使用两端点 `THREE.Line`，不进行球面插值，不生成贴球曲线。
- 总览不绘制全局作品关系；193 个作品节点、十二层直线骨架、事实次级关系网和低亮面板边界继续构成天球。
- 点击作品后，镜头沿该作品的球面法向旋转并从总览距离 `500` 拉近至 `380`；只有该作品的真实入站、出站作品关系以直线显示。
- 聚焦状态保留右侧关系与事实入口，事实正文仍从右侧进入，球面不恢复事实节点命中区。

无头 Chromium 自动交互再次选择《九河盆地》，确认聚焦标题和详情同步更新为 4 条引用、10 条被引用、8 个事实入口；事实入口打开的真实正文为 4,712 个非空白字符。总览与聚焦截图分别保留为 `sphere-straight-overview.png` 和 `sphere-straight-focus.png`。这些结果只证明 Prototype（原型）行为，不证明生产 Renderer、正式 Skill 或工作台接入完成。

## 球面折线与局部飞近

用户指出，直线网络仍会吞没过小的作品光点，并提出把连接覆盖在球面、点击后真正拉近局部表面的方向。当前原型据此将作品恒星从纯光晕改成带实体球芯的发光球：总览节点由 `7.4` 个世界单位扩大到 `11.5`，选中节点为 `21`，相关节点为 `15`；实体球芯写入深度，使连接线在节点中心被真实遮挡，而不是继续从光点上穿过。

星座骨架与聚焦作品关系不再使用单条穿球弦，也没有恢复连续曲线。它们先在球面上取有限个路径点，再由 5 至 7 段端点直线拼成球面折线；聚焦关系位于半径 `229` 的球面外层，方向箭头位于末段。总览仍不显示全部 1,104 条作品关系。

## 自研绘制冻结与开源底座重新筛选

用户否决继续手调自研球面绘制，要求优先复用成熟开源方案。当前原型冻结为失败探索证据，不再把自制球面布局、路径路由、遮挡、命中和相机算法继续推向生产。

截至 2026-08-06 的仓库与上游文档核查结果：

- `vasturiano/react-globe.gl`：MIT，GitHub 约 1,424 stars；当前包版本 `2.38.0`，React Peer Dependency（对等依赖）为 `*`，内部复用 `globe.gl ^2.46`。正式 API 已包含 Points、Arcs、Paths、`onPointClick`、`pointOfView({ lat, lng, altitude }, ms)` 和 `pointerEventsFilter`，与 React 19、点击作品、相机飞近、事实线不参与命中等要求直接对应。
- `vasturiano/globe.gl`：MIT，约 3,119 stars；Vanilla Three.js/WebGL 组件。能力与 React 包相同，但在当前 React 19 Renderer 中需要额外生命周期封装，因此没有直接 React 包合适。
- `visgl/deck.gl`：MIT，约 14,358 stars，GPU 数据层和拾取能力强；但官方文档仍明确把 `GlobeView` 标为 Experimental（实验性），并记录多视图和视图切换渲染问题，不适合作为当前稳定底座首选。
- `CesiumGS/cesium`：Apache-2.0，约 15,538 stars，球体、贴地路径和相机能力最成熟；但它以真实地理空间、瓦片、地形和 GIS 为中心，对作品关系天球明显过重。
- `Stellarium/stellarium-web-engine`：真实星空美术和天球交互有参考价值，但仓库采用 AGPL-3.0；在未完成法务和发布方式评估前，不进入产品代码。
- `ofrohn/d3-celestial`：BSD-3-Clause，是真实星图的二维投影工具，不提供当前需要的三维球体飞近与作品关系层。
- `elibol/blowfish`：虽为 MIT 且明确是 spherical graph，但只有 0 stars，最后更新于 2015 年并内置古老 Three.js 副本，不能作为现代生产底座。

当前技术建议是用 `react-globe.gl` 的官方能力替换原型中的 `3d-force-graph + 自制球面图层`，而不是仅复制外观。作品使用 Points Layer；星座与事实网络使用 Paths Layer；选中作品关系使用 Arcs 或 Paths；点击通过 `pointOfView` 飞近；背景通过 Globe Material、Background Image 或 Custom Layer 定制。该建议尚未成为生产依赖决策，下一步应先复制官方最小示例并代入同一份 193/1,602/1,104/1,355 数据做独立 Prototype（原型）A/B。

用户随后授权直接更换原型查看效果。当前 `index.html` 已从本地 `3d-force-graph` 和 `app.js` 切换到官方 CDN 的 `globe.gl@2.46.1` 与独立 `globe-app.js`；旧 `app.js` 保留作为失败探索证据，但不再加载。新原型继续读取同一份真实 `graph-data.js`，由开源 Points、Paths、Arcs、Rings、HTML Elements 和 `pointOfView` 承担球面渲染、遮挡、节点拾取和相机飞近。

首轮自动截图暴露 Three.js 字体层缺少中文字形，十二层名称显示为问号；现已改用 Globe.GL 的 CSS2D HTML Elements Layer（HTML 元素层），中文标签随球面前后遮挡且可点击进入层级。聚焦参数也按官方角度单位校准：总览作品半径 `.72`；选中后当前作品 `.64`、相关作品 `.4`、无关作品 `.18`；关系弧固定贴近球面的高度 `.018`、线宽 `.075`；聚焦相机高度 `.95`。

无头 Chromium 通过搜索选择《九河盆地》，确认 4 条引用、10 条被引用、8 个事实入口和中文层级标签正常，Page/Console Error 均为 0。截图保留为 `globegl-overview-v2.png` 与 `globegl-focus.png`。当前 Prototype（原型）依赖网络 CDN，未安装 `react-globe.gl`、未修改生产 Renderer、未做离线与打包验收，也未证明 1,355 条事实路径在正式 Electron 中的性能。

## 仓库内 Skill Prototype 封装

2026-08-07 用户要求冻结当前视觉探索，不再继续调图，先把现有 Globe.GL 方案组成可由其他 AI 明确调用的 Skill Prototype（技能原型）。该 Skill 必须读取既有 Growth World Pro 蓝图或世界关系物化结果，不负责创作新世界，也不得安装进 Codex。

原型位于 `prototypes/skills/creatx-build-world-constellation/`，没有加入生产 Creative Skill 允许列表、Renderer、工作台注册协议或用户的 Codex Skill 目录。它通过单一 Node.js 脚本执行以下权威流程：

1. 从项目 `.creatx/growth/goals` 发现世界候选。
2. 优先选择完整 `world/materialization/relations.json`；只有该来源不存在时才允许使用冻结蓝图。
3. 多世界项目要求显式指定 `worlds/<世界名>`；明确 Goal 的损坏输入失败关闭。
4. 读取关系节点对应的真实项目文本，把缺失文件列入生成摘要，不补造正文。
5. 生成带所有权标记的独立 Viewer；只覆盖本 Skill 先前生成的目录，不写 `.creatx`。

冻结蓝图降级只投影 `kind: entry` 的作品及显式关系，不生成正文事实，因此必须标记 `degraded: true`。完整物化与蓝图降级是同一 Viewer 的两种输入密度，不是两套 Runtime（运行时）或第二种关系权威。

真实“灰冠诸境”项目重建结果为 193 个作品、1,602 条事实、1,104 条作品关系和 1,355 条事实关系；12 个已经迁入 `.creatx` 的旧层级 `蓝图.json` 路径被如实报告为缺失正文。无头 Chromium 再次选择《九河盆地》，得到 4 条引用、10 条被引用和 8 个事实入口，12 层标签正常，Page/Console Error 均为 0。冻结蓝图独立测试生成 181 个作品、0 条事实并正确标记降级；损坏 JSON 与非本 Skill 输出目录均失败关闭。

Skill 自带当前原型使用的 1774×887 星云全景素材，但仍通过固定 CDN 版本加载 `globe.gl@2.46.1`。因此它需要联网，仍是 Prototype，不是离线包、正式工作台或生产 Live（真实运行）证据。
