# 图片连接故障诊断与项目队列隔离

## 用户观察

《太衡界世界》的漫画任务连续显示 `fetch failed`，但其他会话和同一项目此前能够真实生成图片。不能据此把故障笼统解释为图片 Provider（模型服务）整体不可用。

## 真实证据

- 正式图片队列中，同一项目、同一模型此前已有 63 张图片成功并真实落盘。
- 《玉角鹿过堤》的角色参考和六页漫画在约 0.2 秒内依次失败，每个 Attempt（尝试）只持续 7–25 毫秒；正常生成通常持续 50–120 秒。
- 旧 Runtime（运行时）把 Fetch（网络请求）拒绝统一压成顶层 `fetch failed`，没有保存嵌套 `cause` 中的 DNS、TLS、连接拒绝、连接重置或超时类别。
- 项目队列在一张任务快速失败后立即领取下一张，使一次瞬时连接故障扩散为整批失败。

## 本批决定

1. `image_result_unknown` 继续表示没有取得可信 HTTP 结果；原任务不得自动重试或伪装为未收费。
2. Runtime 从嵌套错误链提取有限白名单诊断类别和标准错误码，不保存原始主机名、请求内容、凭据或任意错误字段。
3. 同项目首个非取消的 `image_result_unknown` 发生后进入 30 秒内存冷却；后续任务保持 `queued`，其他项目不受影响。
4. 冷却结束后继续下一张已授权任务，不重提结果未知的原任务。用户显式重试可以提前解除冷却，但重试任务仍遵守排到项目队尾的既有语义。
5. 第一版不升级数据库，不持久化冷却状态，也不主动修改或重跑正式失败任务。

## 边界

该修复降低瞬时连接故障的连锁影响，并提高下一次故障的可诊断性；它不能从已经只保存 `fetch failed` 的旧记录反推出当时的具体 DNS、TLS 或套接字原因。
