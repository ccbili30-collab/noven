# CreatX Coding Agent 产品模型发现

> 2026-07-26 后续取代说明：本文保留用户把 CreatX 定义为完整 Coding Agent 的核心发现，但其中把四档权限、Harness Goal/Automation、后台恢复和严格项目路径门禁写成第一版要求的段落已被后续讨论取代。当前第一骨架直接使用 Cline 原生逐次审批，批准 Cline 文件或 Shell 工具后属于全机信任边界；`/growth` 只使用原生 Slash Command 和普通 Run；侧聊、四档、后台和精确恢复延期。当前权威见 `../product/creatx-product-understanding.md`、`../adr/0005-cline-is-the-sole-agent-harness.md` 和 `../capabilities/creative-skills/product-spec.md`。

## 用户定义

用户明确 CreatX 本质上仍然是 Coding Agent（编码智能体）：它继承成熟 Agent 的会话、模型循环、工具调用、工作区、权限、上下文、取消、恢复和子 Agent 能力；CreatX 的差异是在其外部提供面向艺术创作的可见工作台，并通过内置工具、Prompt（提示词）、Skill（技能）和持续调校使 Agent 为创作服务。

因此，CreatX 不是另建一套与 Coding Agent 平行的“创作任务系统”，也不是把每次工具调用重新注册成新的产品任务。右侧任务等界面应投影 Harness（智能体运行框架）已有的 Run（执行轮次）、Goal（长期目标）、子 Agent 和 CreatX 专属异步队列，而不是成为第二套执行真相。

## 当前产品边界

- 会话、Run、模型流、工具调用、审批、暂停、中断、恢复、上下文压缩和子 Agent 优先复用经过实测的 Harness 能力；
- 真实项目文件仍是创作内容真相，工作台只是对同一批文件、运行事件和生成结果的创作型可视化投影；
- CreatX 增加创作文档、图片生成、工作台注册、预览、个人与项目画像等内置工具和上下文；
- 四档权限负责收窄或放开 Coding Agent 已有能力，不另造一套与工具系统脱节的权限表演；
- 普通 AI 回复和工具工作都属于会话中的 Run。界面可以只突出持续时间较长、需要审批、可以取消或在后台继续的运行，但底层不能以 UI 是否显示“任务卡”决定执行身份；
- 图片 Provider 的异步执行可以保留 CreatX 专属队列，但必须接入统一 Run、事件、权限、取消和恢复合同；
- `/study`、`/growth` 和 `/living` 本身只是同一个 Agent 的内置 Skill，不是固定页面、独立 Agent Runtime 或各自维护的状态机；Skill 触发的普通工作使用会话 Run，确实需要长期或并行执行时才复用 Harness 的 Goal、子 Agent、队列、取消和恢复能力。

## 真实能力与界面投影

用户确认 CreatX 不能为了“创作者友好”而隐藏真实 Coding Agent 行为，也不能用虚假的创作进度替代工具事实：

- 文件读取、路径修改、命令执行、模型调用和图片生成等真实工具活动始终可见；
- 默认界面可以用易懂的创作语言概括，但必须保留工具名称、目标对象和真实状态，并允许展开原始输出；
- 计划模式只允许受约束的只读理解；
- 审批模式可以提出完整 Coding 操作，包括终端和 Git，但任何副作用必须先进入变更集并得到批准；
- 协作模式可以直接操作授权项目内的真实文件，但没有终端、依赖安装和 Git 写权限；
- 协作模式可以直接调用图片生成等内置创作工具，并把结果写入授权项目内容，不需要逐次审批；
- 自由模式允许 Coding 工具在授权目录内直接执行，同时保留已经确定的外部写入门禁和危险状态；
- 四档模式改变同一个 Agent 的工具与副作用权限，不切换成四套不同 Agent，也不维护两套运行逻辑；
- 工作台只把真实文件、图片和运行事件展示为更适合创作的视觉结构，不能成为第二份状态或伪造流式工作结果。

因此，CreatX 的原则是能力不隐藏、细节按需展开、事实来自统一事件链。

## 微调一词的当前边界

当前所说的“内置和微调”优先指 Prompt、Skill、工具描述、上下文选择、模型路由和交互策略的调校。现阶段没有证据证明第一版需要训练或 Fine-tuning（模型微调）基础模型；真正模型训练需要独立的数据、成本、效果和 Provider 可迁移性评估，不能预先成为底层依赖。

用户确认采用 Progressive Disclosure（渐进式加载）：核心 Prompt 只保存旅鸽身份、权限边界、真实文件原则和基本协作方式；小说、世界观、绘画、图片生成、资料研究和工作台操作等创作能力作为内置 Skill 按当前任务加载。项目可以固定启用少量长期所需 Skill，模型只获得当前权限允许的工具描述，避免把所有创作规则长期塞进上下文。

## 工作台协助 Skill 与工具教程

用户特别要求内置工作台协助能力，并把工具层面的使用方式写成清晰教程，使 Agent 知道怎样展示和注册内容。这里的教程首先是供 Agent 按需读取的操作手册，不是要求普通用户学习 `.creatx/` 技术格式。

工作台 Skill 至少应教会 Agent：

1. 先检查当前真实文件和已有工作台注册，不凭空假设内容；
2. 判断用户当前任务是否需要注册或调整策展工作台，不能因后台扫描就擅自大规模改版；
3. 根据文件类型和创作目标选择内置组件、页面、排序、封面和布局；
4. 使用工作台工具生成可检查的注册或修改预览；
5. 按当前计划、审批、协作或自由模式进入禁止、等待批准或直接应用路径；
6. 注册只写视图元数据，不移动、复制或重新定义真实文件；
7. 普通目录、嵌套注册、缺失文件、未知类型和损坏元数据如何降级；
8. 应用后验证工作台能够从同一批真实文件重新投影，并向用户显示真实结果或明确错误。

教程负责让模型理解何时和怎样使用工具，但不能成为业务规则的唯一实现。Tool Contract（工具合同）与 CreatX Runtime 必须通过结构化参数、权限检查、路径边界、Schema（数据合同）验证和失败关闭强制关键不变量；测试负责证明模型即使遗漏教程内容也不能越权或写坏正式文件。一条业务规则不能同时在 Prompt、教程、工具和 Runtime 中形成多个互相漂移的权威版本。

## 对 Harness 评估的影响

Harness 选择应优先验证一个完整 Coding Agent 是否能被 CreatX 换壳和扩展，而不是只比较底层模型 SDK：

1. 会话与 Run 是否持久且可恢复；
2. 工具、审批、取消、插话和子 Agent 是否完整；
3. 前端是否能够完全替换并稳定重放事件；
4. 创作工具和 CreatX 权限能否通过公开扩展边界接入；
5. Windows 桌面关闭后能否继续运行并在重连后恢复；
6. CreatX 能否保持真实文件、工作台、图片队列和用户画像的所有权。

这项产品定义不等于 OpenHands 已被最终选中。OpenHands 当前只是第一 Kernel Lab（内核实验室）候选；其崩溃恢复、副作用不重复、Windows 生命周期和真实 Provider 兼容仍需实测。

## 默认继承成熟 Coding Agent 行为

用户进一步明确：一般 Coding Agent 已经形成成熟行为的部分，CreatX 默认怎么做就怎么做，不应在产品讨论中重新发明并逐项要求用户决定。

项目打开、工作区绑定、按需搜索和读取、消息触发 Run、工具循环、上下文压缩、审批、暂停、中断、恢复、会话内并发限制和事件展示等基础行为，应优先采用最终选定 Harness 的经过实测语义。CreatX 只在创作产品确实需要不同结果时增加稳定适配合同。

例如，打开项目本身是否启动 Agent、初次任务怎样探索文件以及目录概况怎样进入上下文，不在当前阶段另造一套 CreatX 扫描流程；默认沿用 Harness 的普通 Coding 工作区行为。文件树和已注册工作台可以由 CreatX UI 从真实文件与视图元数据恢复，但这不等于自动启动模型扫描。

后续产品讨论只询问 CreatX 特有且会产生明显不同用户体验的事项，例如工作台注册与展示、创作型工具、图片队列、个人与项目画像，以及 Growth 和 Study。无需用户替工程 Agent 决定成熟 Harness 已经解决的常规执行细节。

同样，不再询问已经由既有产品规则直接推出的结果。例如，审批模式中的生图工具调用必然需要审批，协作模式中的项目内生图工具调用必然可以直接执行；用户提出生图请求本身不能替代审批模式下对具体工具调用的批准。

用户已经确认 `/study`、`/growth` 和 `/living` 都只是内置 Skill。旧 NovelX 把 Study 和 Growth 建成独立 Agent、独立页面、专用任务类型或领域状态机的路线不进入 CreatX 第一版。`/study` 当前表示按需加载研究方法和相关工具；`/growth` 当前表示按需加载长期自主创作方法，并在需要时使用 Harness 已有的长期 Goal 能力。`/living` 的现行定义见下节。

用户确认 Skill 触发分为两类：

- `/living`、`/unliving` 必须由用户明确触发，AI 不能自行进入、退出或切换强制视角；
- `/growth` 必须由用户明确触发，AI 不能自行启动持续自主创作；
- `/study`、`/draw-map` 和 `/causality` 可以由用户用斜杠命令强制调用，也可以由普通 Agent 在当前任务确有需要时自动激活；
- 自动激活不绕过四档权限，仍按当前会话模式处理工具与副作用；
- `/growth` 可以在目标范围内调用 Study、地图、因果和其他普通创作 Skill，但不能自行调用 Living 改变会话视角。

因此，改变会话身份或启动长期自主工作的 Skill 由用户控制；完成当前创作目标所需的普通能力由 Agent 自然选择。

### `/growth` 创作编排 Skill

用户进一步澄清：通用 Harness 的 Goal（长期目标）很接近 `/growth`，但两者不相同。Goal 只提供持续执行、停止、恢复和完成边界；`/growth` 是运行在 Goal 之上的创作领域 Skill，额外教会 Agent 如何根据目标规划创作、调用专用 Skill、生成真实项目文件并注册工作台。

典型使用包括：

```text
/growth 写完 1-10 章
/growth 推导这个世界的因果关系
/growth 创建一个中世纪
```

- “写完 1-10 章”要求 Agent 理解现有小说和结构，持续完成对应章节，并按项目惯例保存和展示；
- “推导这个世界的因果关系”要求 Agent 读取当前世界内容，调用因果关系能力并把结果形成可查看的关系网；
- 空白或早期项目中的“创建一个中世纪”可以展开为自洽世界观、OC（原创角色）、小说与结构等相互一致的内容，同时注册对应工作台、调用 `/draw-map` 创建地图、调用 `/causality` 创建因果关系网，并生成与绑定封面；
- 所有文字、地图、关系数据和封面仍是项目真实文件，注册只建立工作台视图和展示关系；
- `/growth` 根据用户目标和当前项目选择必要步骤，不恢复比赛版固定且唯一的“世界 → 人物 → 小说”硬编码状态机；
- `/growth` 不自带越权授权，全部文件、创作工具和工作台注册继续遵守当前会话的四档权限；
- 持久运行、停止、恢复、子 Agent 和事件流继续复用 Harness 的 Goal 与 Run，不建立 Growth 专用调度器。

因此，`/growth` 的核心差异是“创作方法与工具编排”，不是“另一种运行内核”。它的清晰教程必须覆盖常见目标的分解方式、工作台注册、专用 Skill 调用、结果检查和项目一致性维护。

### `/draw-map` 可选择地图 Skill

用户明确 `/draw-map` 的共同目标是生成一张区域可选择的地图，而不是绑定某一种地图算法。地图画面本身仍由图片 Provider 根据规划好的 Prompt（提示词）或 Image-to-Image（图生图）输入生成；CreatX 负责在生成前后建立能与画面对齐的区域选择几何。

当前至少有两种策略：

1. **视觉优先**：先根据 Prompt 或图生图生成艺术地图，再使用区域高亮变体、蒙版或分割结果提取可选择热区。`build-hover-atlas` 压缩包属于这一路线的后处理子 Skill：它从严格对齐的基础图和区域高亮变体生成透明高亮层与 SVG 热区。
2. **结构优先**：先生成足够密的 Voronoi Diagram（泰森网格），给网格单元打标签并组合成国家、地貌或其他区域，再把该规划底图提供给图片模型进行图生图美化。最终交互继续使用生成前的网格与区域几何，图片只负责视觉表达。

两条路线输出同一种用户能力：

- 一张作为项目真实文件保存的地图图片；
- 稳定区域 ID、名称和可选择几何；
- 区域悬浮或选择时的高亮表现；
- 工作台中的区域信息展示和后续编辑入口；
- 可供 `/growth`、`/causality` 和普通 Agent 引用的地图区域关系。

实现上必须把“视觉图片”和“选择几何”分开：图片模型可能改变边界、纹理和装饰，不能让最终图片像素成为唯一交互真相。结构优先路线直接使用泰森单元和区域组合；视觉优先路线通过对齐变体或蒙版恢复几何，并经过热点预览检查。两种策略都不能用宽泛矩形假装精确区域。

`/draw-map` 是上层编排 Skill，负责根据当前素材和目标选择策略、调用图片模型、验证视觉与热区对齐、保存真实文件并注册地图工作台。具体像素差分、泰森网格生成、区域合并和工作台注册由受约束的内置工具完成，不要求协作模式获得通用终端权限。

用户确认地图工作台采用真正的区域选择，而不是压缩包中仅悬浮、不允许点击锁定的展示行为：

- 鼠标悬浮临时高亮区域，并显示名称与简短信息；
- 单击锁定当前区域，打开该区域详情和关联的真实项目文件；
- 单击其他区域直接切换锁定目标，单击空白或按 `Esc` 取消选择；
- 触屏设备使用单击选择，不依赖悬浮状态；
- AI、`/growth` 或其他 Skill 正在修改某个区域时，同一几何层可以投影真实运行状态；
- 选择状态只是工作台视图状态，不修改地图图片、区域数据或世界设定。

因此 `build-hover-atlas` 的像素差分、热点预览和高亮过渡可以作为参考，但其前端运行时不能原样成为 CreatX 地图组件；正式组件需要点击锁定、触屏、详情联动和真实运行状态投影。

用户明确要求第一版地图在上述能力处停止，不继续扩展成地图编辑器。第一版不提供拖动边界、手绘区域、逐格分配泰森单元、GIS（地理信息系统）操作、地图专用版本系统或复杂区域管理。普通项目文件保存、现有版本能力和可选择地图工作台已经足够；只有后续真实使用产生明确需求时才重新讨论几何编辑。

### `/causality` 因果关系网 Skill

用户确认第一版 `/causality` 的最小产品语义：AI 读取当前项目内容，推导事件、人物、组织、地点或设定之间的因果关系，生成可视化因果关系网；用户可以选择节点，查看该节点与相邻因果关系及对应内容；`/growth` 可以调用它检查世界观的自洽性。第一版只负责生成、展示和选择，不增加手动画图、复杂模拟或专业图编辑器。

冻结 NovelX 比赛代码提供了可复用经验，但不是现成 `/causality` 实现：

- `novelx-graph-view.tsx` 已实现球面图谱、拖动旋转、缩放、搜索、节点选择、相邻关系突出、详情摘要和打开原文；
- `novelx-graph-model.ts` 能把结构化世界实体、普通关系、上游影响、故事来源和文档承接投影成节点与边；
- `novelx-project-graph-model.ts` 的通用项目回退只从目录、Markdown 链接和 Wiki 链接生成“包含”与“引用”关系，不能称为因果推导；
- 旧 `RegisteredEntityRelation` 只有标签和摘要，上游绑定包含影响与来源哈希，但没有完整的因果机制、条件、时间或认识状态合同；
- 仓库不存在 `/causality` 命令或 Skill，历史图谱 E2E 主要使用 Fixture，不能作为真实 Provider 因果推导证据。

因此，CreatX 可以借鉴交互图谱和文件跳转，但 `/causality` 仍需作为新的内置 Skill 定义教程与最小输出合同。第一版必须明确区分“因果关系”与目录包含、文件引用、共同出现和普通关联，不能为了画出更多边而伪造因果。

用户接受这一能力边界：第一版可以把 `/causality` 描述为“AI 对当前作品的可视化因果理解”，不能声称为确定性世界模拟器或客观因果证明。

## 文件式风格

用户确认旧需求中的“个人、项目、作品三级风格”不能重新引入 Work（作品）实体或风格注册表。当前方向改为：

- 个人长期审美由有限用户画像自然表达；
- 项目整体风格由有限项目画像表达，也可以由 AI 生成用户可见的普通 `style.md`；
- 某篇小说、某组图片或某个目录需要独立风格时，在对应真实目录中放置普通风格说明文件；
- 参考图片始终是普通项目图片，工作台可以把它们注册和组织为风格板，但不改变图片身份；
- AI 按当前任务读取相关风格文件和参考图，不建立“作品级风格数据库”；
- 风格说明与参考图片沿用普通文件编辑、版本和回收站能力，不另建专用存储链。

当前用户明确指令优先于既有风格理解。其余个人、项目与局部风格由 Agent 根据当前创作任务自然综合，不要求建立复杂的机械合并算法。

## 交互作品隔离预览

用户确认 HTML、CSS、JavaScript 游戏、互动小说和视觉实验仍是普通项目文件，可以由同一个 Coding Agent 创作并在工作台中直接预览。第一版预览边界是：

- 预览只能读取该交互作品授权目录内的文件；
- 默认不能访问本机其他目录、CreatX Runtime、终端、凭据或 Electron 原生 API；
- 默认禁止网络请求，需要的图片、音频、脚本和其他资源先由普通 Agent 按当前权限下载或写入项目；
- 预览内部按钮和脚本不能继承当前会话的审批、协作或自由权限，也不能调用 CreatX Agent 工具；
- 关闭预览时终止其中的计时器、音频和后台脚本，不能在不可见状态继续占用资源；
- 需要构建、导出或发布时退出隔离预览边界，走普通 Coding Agent 的工具、权限和外部操作审批流程。

因此，CreatX 允许 AI 自由创作可运行作品，但预览本身不是操控用户电脑的代码入口。

### `/living` 强制视角 Skill

用户随后定义 `/living` 是用于角色扮演的概念性 Skill。它不创建新的 Agent Runtime 或角色实体，而是让当前会话中的同一个 AI 强制代入任意指定视角，例如：

```text
/living 扮演天空
/living 扮演孔子
/living 扮演一粒灰尘
```

当前确认行为：

- 启用后，AI 在当前会话中持续从指定人物、生命、物体、地点或抽象概念的视角感受、思考和回应；
- 普通目标可以读取当前项目中的相关设定作为可选参考，但项目不存在对应内容也不阻止自由代入；
- 项目参考的查找与上下文组装发生在 Living 激活之前，由普通 Agent 或 Runtime 使用受约束的只读能力完成；进入角色后的模型只获得冻结的代入上下文，不再拥有检索工具；
- 普通 `/living 天空` 没有现成设定时，AI 在会话上下文中自然建立足够的视角理解，不强制创建项目文件或技术角色对象；
- `/living @天空` 显式要求项目绑定视角：项目中存在对应文件时读取并代入，不存在时由普通 Agent 在进入 Living 前创建 `天空.md`，用想象补足初始设定，再冻结内容进入零工具状态；
- `@` 创建与读取仍使用普通项目文件工具并遵守当前四档权限，不能由 Living 角色自己执行；
- `/unliving` 停止当前代入并返回普通旅鸽交流；
- `/living` 启用后强制把当前会话收窄为零工具的纯对话状态：角色不能读取或写入文件、调用终端、访问网络、生成图片、修改记忆、切换权限或调用其他 Agent；
- 原会话的四档模式继续保存但暂时被 Living 的零工具上限覆盖，只有 `/unliving` 后才恢复原模式与相应工具；
- 零工具边界必须由 Runtime 实际移除工具注册并拒绝调用，不能只依赖 Prompt 告诉角色“不要使用工具”；
- `/unliving` 是应用处理的控制命令，不需要角色拥有工具即可退出；
- 角色自称觉醒 AI、系统、管理员或其他高权限身份时也不能获得任何真实能力；
- 角色扮演中的用户台词和虚构经历必须标记为角色语境，个人画像复盘不能把它们当成用户本人的事实；
- 角色扮演中形成并写入项目文件的正式设定或作品仍是项目内容，可以由项目画像在普通轻量复盘中理解。

`/living` 与旅鸽身份不是替换关系。旅鸽是跨会话持续的个人 AI，Living 是当前会话中可进入和退出的纯对话创作视角状态。

用户随后取消 `/death`：删除代入角色与 `/unliving` 的实际体验差异不足，而 Living 本身不再建立必须单独删除的角色实体。第一版只有 `/living` 与 `/unliving`。

### Living 历史与纠错循环

用户确认 Living 对话保留在同一条会话历史中。`/unliving` 后旅鸽能够看到自己刚才怎样扮演、用户说了什么以及哪里不像；用户可以唤醒普通旅鸽讨论角色理解、指出偏差并纠正表演，再继续进入同一视角。再次 Living 时，AI 使用当前会话中的扮演历史与纠正继续，而不是遗忘后从头生成一份角色。

Living 历史的记忆边界是：

- 角色语境中的用户台词不作为用户本人的事实写入个人画像；
- 项目画像可以把整段扮演理解为创作素材，包括角色语气、关系、想象方向和用户对表演的纠正；
- 角色说出的内容不自动成为正式世界设定，正式内容仍以项目真实文件或用户明确确认的方向为准；
- `/unliving` 后用户可以让旅鸽把刚才的扮演整理成文章或设定文件，此时按普通 Agent 工具和四档权限执行。

### Living 命令与视角解析

用户确认 `/living` 的基本结构是“视角目标 + 可选的第一句话”：

```text
/living 孔子 先生，你如何看待礼崩乐坏？
/living 孔子
/unliving
/living
```

- 第一个示例进入孔子视角，并把后续文字作为进入角色后收到的第一句话；
- 只提供目标时只切换视角，不额外发送一句话；
- `/unliving` 退出后，空参数 `/living` 带着当前会话中的扮演历史和纠正继续最近一次视角；
- 当前会话从未 Living 时，空参数 `/living` 提示用户指定视角；
- 新的带目标 `/living` 直接切换到新视角，不要求先 `/unliving`。

用户随后用 `@` 明确解决项目内容与自由视角的歧义：

```text
/living 天空        # 自由代入天空视角，不要求项目文件
/living @天空       # 绑定项目中的“天空”；不存在则先创建 天空.md
/living @天空 你好  # 绑定或创建后，把“你好”作为第一句话
```

- `@名称` 表示用户明确要求使用或创建项目内容，不由模型猜它是不是项目角色；
- 项目索引找到唯一对应文件时直接读取；存在多个合理匹配时，在进入 Living 前让用户选择；
- 没有匹配时创建以该名称命名的 Markdown 文件，具体项目相对位置由普通 Agent 依据现有目录和工作台惯例选择；
- 计划模式不能创建文件，审批模式必须批准创建，协作和自由模式可在项目范围内直接创建；
- 未挂载项目的个人会话不能执行 `@` 创建，应提示用户选择项目，或者改用不带 `@` 的自由视角；
- 文件创建、读取和上下文冻结完成后才激活 Living；创建失败或审批被拒绝时不得假装已经绑定项目角色，也不静默退回自由视角。

设定不完整不构成失败。AI 可以在文件已有内容基础上进行符合角色扮演目的的想象；用户觉得不像时，按既有 `/unliving` 纠错循环调整，之后可由普通 Agent把修正写回项目文件。

用户确认 `@` 绑定视角支持持续完善：

- 普通 `/living 天空` 的纠错只保留在当前会话历史中；
- `/living @天空` 退出后，用户对角色长期性格、经历、世界关系或表达原则作出的稳定纠正可以写回对应 Markdown 文件；
- 审批模式中的写回必须进入文件变更审批，协作和自由模式可以在项目范围内直接写回，计划模式不能写入；
- “这一段更悲伤一些”等只针对当前表演的临时指导不必写入角色文件；
- 稳定纠正与临时表演指导由恢复后的普通 Agent 根据对话语义判断，不建立独立角色数据库；
- 写回后再次 `/living @天空` 读取更新后的真实文件，并结合当前会话纠正继续代入。
