# 图片回执对账重复冲突与严格恢复

## 用户问题

《赫尔墨斯环城》迁入普通 Profile 后，打开项目会连续显示 `image_queue_conflict: image task is already bound to a different document attachment`。错误卡反复覆盖当前界面，已经妨碍正常阅读。

## 现场事实

- 正式项目有 97 份 GWP 物化回执。
- 95 个图片任务已成功，另有 1 个 Provider HTTP 失败和 1 个历史中断。
- 92 个成功任务的旧附件意图使用了 Markdown 标题语法，例如 `# 环城剖面与重力标注`；挂接服务要求纯标题文本，因此留下 `image_attachment_conflict`。
- 这些任务和正式回执指向同一文档，但旧图注、位置锚点与回执重新派生的规范意图不同。项目每次打开都会对账全部回执，并把每个冲突分别投影成全局错误。
- 95 份成功图片对应的 Markdown 已有有效图片引用。92 份历史修复引用使用未编码中文路径；旧幂等实现只识别图注和编码路径完全相同的引用，直接重挂会重复插图。

## 接受的恢复语义

GWP 正式回执继续是正文—图片关系权威。恢复入口不得放宽普通附件绑定：

1. 不存在附件意图时，按回执首次绑定。
2. 已成功挂接且仍是同一文档时，保持既有成功记录，不因图注或锚点表现差异重新写正文。
3. 同一文档的待处理意图可以规范为回执意图；图片未成功时不执行挂接，也不清除 Provider 错误。
4. 只有图片已成功、旧附件状态为 `failed` 且错误码精确为 `image_attachment_conflict` 时，才把同文档意图规范化为待处理并重挂。
5. 不同文档、取消任务、其他附件错误类别继续失败关闭。
6. Markdown 已经引用同一相对图片路径时，无论图注不同或中文路径是否 URL 编码，都按幂等成功，不重复改写正文。

本恢复不直接修改正式 SQLite、不删除历史 Attempt、不把图片 Provider 失败或中断伪装为成功。

## 验收边界

在正式 Profile 的完整副本中执行 97 份真实回执：95 个成功图片挂接全部收敛为成功，1 个失败和 1 个中断保持原任务状态，全部 Markdown SHA-256 不变。正式 Profile 只有在包含本修复的应用启动并打开项目后才会执行相同恢复。
