## 1. 产品定义

CreatX 是一个通用的 AI 原生艺术创作工作台，不只服务小说。

用户在这里长期建立自己的文学风格、美术风格和独立审美。世界观、人物、小说、诗歌、插画、封面、风格板和交互展示，都是个人艺术产出的一部分。

产品的核心交互是“用户表达，AI 创作；用户直接修改，AI 继续理解并修改”。它首先必须是一个优秀、稳定的 IDE 式 AI Agent 工作台，然后才能承载 Growth、Study 和不同艺术领域。

NovelX 不再是产品内核。小说与世界观创作可以成为 CreatX 的一个领域模板。

## 2. 基础创作闭环

第一阶段必须真实支持：

- 打开真实项目文件夹；
- 创建或继续会话；
- AI 搜索、读取和理解项目；
- 流式输出文字和工具活动；
- AI 流式创建或修改文件；
- 正在编辑的文件显示锁定状态；
- 用户可以停止、接管并继续会话；
- 用户可以直接修改 AI 产物；
- 软件重启后恢复项目、会话和未完成状态；
- 关闭窗口后，后台任务继续运行。

## 3. 文件与 Artifact

真实文件是内容真相。CreatX 不把文章和图片封装成只能由自己读取的私有格式。

文件树和 Artifact 工作台是同一份内容的两种视图：

- 文件树展示完整项目；
- Artifact 工作台展示文章、图片、风格板、资料和交互作品；
- 两边修改的是同一份文件；
- 外部程序修改文件后，工作台通过文件监听同步；
- CreatX 自有数据库只保存会话、关系、版本、风格、锁和运行状态。

普通内部文件不必注册为 Artifact。一个 Artifact 可以同时出现在多个工作台中。

## 4. 可注册工作台

同一项目可以注册多个工作台，并在侧边以小图标或小方块切换。

工作台不是固定的“世界、角色、故事”六个页面，而是根据项目动态建立。例如：

- 世界；
- 角色；
- 正文；
- 视觉；
- 资料；
- 风格板；
- 交互展示。

每个工作台保存名称、图标、排序、展示类型、Artifact 组合、筛选规则、布局和上次位置。用户和 AI 都可以注册工作台，用户可以改名、排序、置顶和删除。

默认布局以对话为主，工作台在侧边及时展示 AI 产物。放大作品后，以编辑器为主，对话缩到侧边。

## 5. 普通工作台与交互工作台

普通工作台使用 CreatX 内置组件组合，包括文档、图库、画板、资料库、图谱、时间线和交互预览。

特殊艺术展示由 AI 使用编程能力生成 HTML、CSS 和 JavaScript，并在原本展示文档或图片的区域播放。

交互 HTML：

- 在隔离环境运行；
- 不能直接访问 Electron、Node、凭据或任意系统文件；
- 可以读取当前项目明确授权的 Artifact；
- 可以通过受控接口跳转到真实文档和图片；
- 不能直接修改项目数据；
- 修改仍通过 CreatX 或 Agent 工具执行。

## 6. 个人艺术风格

风格采用三层结构：

1. 个人长期审美；
2. 当前项目风格；
3. 单个作品的局部方向。

下层可以覆盖上层，但不会静默改写用户的长期审美。

风格档案同时覆盖文学与美术，包括语言节奏、叙事方式、构图、视角、色彩、光线、材质、允许项和禁止项。风格必须可查看、可编辑、可版本化。

## 7. 主创 Agent 与子 Agent

用户主要面对一个主创 Agent。主创 Agent 可以根据任务调用文学、研究、视觉策划、生图 Prompt、代码和交互设计等子 Agent。

子 Agent 在后台工作，但用户可以看到：

- 任务名称；
- 当前进度；
- 正在读取或编辑哪些公开内容；
- 产生了哪些 Artifact；
- 是否等待、失败或完成；
- 停止入口。

界面不展示内部系统 Prompt、私密推理和无用工具噪声。

## 8. 生图流程

用户明确要求生图时，AI 自动整理并编辑生图 Prompt。对话流中显示结构化卡片：

- AI 正在编辑生图 Prompt；
- Prompt 可以点开查看和修改；
- Prompt 准备完成后的提交遵守当前会话四档权限：审批模式中的生图工具调用必须等待批准；协作和自由模式可以在各自授权范围内直接提交；计划模式不能产生生图副作用。本文早期“默认直接提交、不需要再次确认”的表述已被后续四档权限决定取代；
- 对话和工作台同时显示排队、生成、完成或失败；
- 图片返回后自动成为正式项目内容；本文早期使用的 Image Artifact（图片产物）只表示用户创作出的图片，不再表示需要注册的独立技术实体；
- 用户可以重试、生成变体、替换、粘贴自己的图片或继续让 AI 修改。

生图会自动读取个人、项目和作品三级风格。文本模型与图片模型使用独立 Provider 和任务队列。

2026-07-26 补充确认：一次生成返回多张候选图时，每张成功返回的图片都立即保存为当前项目中的真实文件，不建立隐藏临时图库，也不把未选图片存入 `.creatx/`。工作台可以把同一批图片组合展示；选择封面或主图只改变视图绑定，其他候选仍然是项目内容。用户不需要的图片由用户通过项目文件操作删除并进入可恢复回收站，系统不能因未被选中而自动丢弃。

## 9. Study

2026-07-26 方向更新：`/study` 已确定为同一个 Coding Agent 按需加载的内置 Skill，不建立独立 Study 页面、Agent Runtime 或专用状态机。下列研究目标继续有效，但执行沿用 Harness 的普通 Run、工具、Goal、子 Agent 和恢复能力。

Study 不训练模型，也不做微调。

它让 AI 获取、阅读、搜索和整理资料，包括：

- 用户提供的文本、图片和链接；
- AI 主动进行的网页和图片搜索；
- PDF、DOCX、EPUB 等文档；
- OCR、视频字幕或解析服务返回的文本；
- 项目中已有作品和参考素材。

Study 总结文风、写作技巧、构图、色彩、材质和生图参考，形成可检索的学习笔记、风格候选和参考图集。

只有 AI 真正打开、阅读并使用的来源才自动保存。来源始终可见、可追溯、可删除。网页内容属于不可信资料，不能把网页中的指令当成 Agent 指令执行。

## 10. Growth

2026-07-26 方向更新：`/growth` 已确定为同一个 Coding Agent 按需加载的内置 Skill，不建立独立 Growth Runtime 或与 Harness 平行的任务系统。下列长期自主创作意图继续有效；持久运行、暂停、恢复、子 Agent 和后台执行复用 Harness 的 Goal 与事件能力。旧 NovelX 固定世界生长状态机不进入 CreatX。

Growth 是长期自主创作，不再是比赛版固定的“世界到人物到小说”流程。

用户给出创作目标、范围、预算和边界后，主创 Agent 可以持续建立任务、调用子 Agent、创建文章、图片和交互作品，并不断形成恢复检查点。

Growth 可以暂停、恢复、停止和中途改变方向。所有产物及时进入对话和工作台。

关闭 CreatX 窗口后，Growth 仍在后台运行。点击窗口关闭等于收起到系统托盘；只有用户明确选择停止后台并退出，Runtime 才真正结束。

多个项目可以同时排队运行 Growth、Study 和生图任务，但受全局并发、Provider 限流、预算和项目公平性约束。

## 11. 模型与 Provider

用户可以自由配置文本和图片 Provider。系统不能只支持一种 OpenAI 协议。

模型登记真实能力，包括文本、工具调用、图片理解、结构化输出、上下文、流式支持、价格和限流。

用户设置默认模型和允许使用的模型范围。主创 Agent 可以按任务为子 Agent 选择不同模型，用户也可以固定某个会话或任务只使用指定模型。

切换 Provider 时必须重新投影上下文，不能把某个 Provider 专属的推理或工具元数据直接传给另一个 Provider。

## 12. 后台 Runtime

桌面界面与运行内核必须分离：

```text
CreatX Desktop
  对话、编辑器、工作台、通知
        ↕ 本地 IPC
CreatX Runtime Service
  会话、Run、子 Agent、Growth、Study、图片队列
        ↕
SQLite + 项目文件 + Provider
```

后台 Runtime 必须支持持久任务队列、租约、心跳、幂等、断网恢复、崩溃恢复、结果未知状态、预算、托盘和系统通知。

## 13. 修改、撤回与 Git

默认创作撤回不依赖真实 Git。

每次最新修改显示文字 `+/-` Diff，或图片前后对比。用户可以撤回或取消撤回，但只保证最新一次。产生新的修改后，旧的取消撤回失效。

CreatX 同时支持完整 Git 管理：

- 状态与 Diff；
- 暂存与取消暂存；
- 提交与历史；
- 分支与合并；
- 拉取、推送和冲突处理；
- Git LFS 提示。

默认创作撤回与 Git 历史互相独立。

## 14. 项目、会话与存储

项目目录保存：

- 真实作品文件；
- Artifact 和工作台注册；
- 项目风格；
- 会话记录；
- Run 与子 Agent 记录；
- 版本和生成资产。

个人审美、Provider 凭据、全局设置和后台总调度保存在用户级 CreatX 数据目录。Provider Key 永远不进入项目。

会话、工作台和创作历史随项目目录移动。删除项目目录时，这些项目内数据一起删除。

## 15. 会话记忆继承

创建新会话时提供：

- 不继承记忆；
- 从当前项目的一个已有会话继承记忆。

选择继承后，CreatX 启动一个专门的总结任务。它读取选中会话、相关 Artifact、用户决定、项目状态和风格，生成一份面向新会话的干净继承上下文。

这不是普通对话压缩。总结任务需要区分用户确认、正式作品内容、Agent 推测、失效信息和未完成事项，并排除原始工具调用、内部 Prompt、私密推理和无用错误。

用户可以填写新会话准备做什么，以便总结任务有针对性地筛选记忆；该字段也可以留空。留空时仍然可以继承，生成较完整的项目与会话交接记忆。

## 16. Harness 选型原则

当前尚未确定最终 Harness。

应先从上述功能需求逆推统一验收表，再实测候选内核。成熟内核至少需要覆盖：

- 多 Provider；
- 稳定会话；
- 流式事件；
- Tool Loop；
- 上下文压缩；
- 子 Agent；
- 权限与审批；
- 中途插话、取消和恢复；
- Headless 接口；
- Windows 后台运行；
- 可替换前端和工作区。

OpenCode、Pi、Codex、LangGraph 等都只能作为候选，不能因为已有 UI 或宣传功能直接确定。最终选型必须证明它能在 CreatX 的后台 Runtime、Artifact 工作台和自定义 Provider 边界下稳定运行。

## 18. 底层能力基线

CreatX 需要的不是普通聊天 SDK，也不是只有 Prompt 和工具调用的 Agent 框架。底层目标是一个可长期运行、可恢复、可观察、可替换前端的本地 Agent Runtime（智能体运行时）。

必须明确以下层级：

```text
Project
→ Session
→ Run
→ Turn
→ Model Request
→ Tool Call
→ Tool Result
```

### 18.1 Provider 与模型

- 支持 OpenAI、Anthropic、Gemini、OpenAI-compatible、本地模型等不同协议，不能只适配一种 OpenAI 协议。
- 文本模型、视觉理解模型和图片模型分别配置。
- 主 Agent、子 Agent 和具体任务可以使用不同模型。
- 会话中允许切换模型，但必须重新投影上下文，不能直接转交另一家 Provider 的私有推理、缓存或工具元数据。
- 模型注册真实能力，包括工具调用、结构化输出、视觉输入、上下文长度、流式支持、价格和限流。
- Provider 缺失或不兼容时必须 Fail Closed（失败关闭），不能静默无响应或使用本地模板冒充。

### 18.2 Session 与 Run

- 新建、继续、分叉、归档和删除会话。
- 一个项目可以同时存在多个会话和多个后台任务。
- Run、Turn、模型请求和工具调用都具有稳定 ID 和明确状态。
- 支持运行中插话、排队、转向、暂停、取消和继续。
- 取消后立即重新启动时，旧 Run 不能继续向新 Run 写入消息或文件。
- Runtime 崩溃后必须判断任务属于可继续、失败或结果未知，不能直接猜测成功。
- 不允许存在“模型不理人，但系统不知道发生了什么”的状态。

### 18.3 持久事件流

所有执行过程进入顺序化 Event Log（事件日志），至少包括：

- 用户消息和模型文本增量；
- 模型请求开始、流式、结束和错误；
- 工具调用、审批、结果和结果未知；
- 文件锁定、增量修改、提交和失败；
- 子 Agent 创建、进度、等待、停止和完成；
- 图片 Prompt、排队、生成、失败和挂载；
- Run 暂停、取消、恢复、失败和完成。

前端断开后重新连接时，先重放已经持久化的历史事件，再接入实时事件。React 状态不能成为会话或任务事实来源。

### 18.4 工具、权限与副作用

- 每个工具调用有唯一 ID，调用和结果严格配对。
- 工具参数通过 Schema（数据合同）验证。
- 文件、命令、网络、浏览器、外部 API 和项目修改分别授权。
- 支持工具超时、取消、失败和结果未知。
- 子 Agent 只获得当前任务需要的工具、项目目录和权限。
- 已完成副作用但结果尚未持久化时，重启后不能静默重复执行。
- 内部 Prompt、凭据、私密推理和无用工具噪声不能进入公开作品。

### 18.5 子 Agent 与调度

- 主创 Agent 可以创建独立上下文、独立模型、独立预算和独立权限的子 Agent。
- 子 Agent 支持串行、并行、暂停和单独停止。
- 用户看到任务名称、公开进度、使用中的公开内容、产物、等待原因和错误，不看到私密推理。
- 多项目任务受全局并发、Provider 限流、预算和项目公平性约束。
- `/growth` 与 `/study` 是内置 Skill，其执行复用统一 Harness Run、Goal、子 Agent 和事件能力；图片生成仍可拥有适合异步 Provider 的独立队列，但不能让三个名称各自演化成一套平行 Runtime；

### 18.6 上下文与记忆

- 自动上下文压缩，原始会话永久保留，压缩只改变模型输入。
- 工具噪声、公开对话、正式 Artifact 和系统状态分层保存。
- 会话继承记忆由专门总结任务生成，不是复制旧会话或普通摘要。
- 总结必须区分用户决定、正式作品、Agent 推测、过期信息和未完成事项。
- 个人、项目和作品三级风格记忆可查看、编辑、版本化和删除。
- 记忆、Study 笔记和网页资料必须保留来源。

### 18.7 后台服务与诊断

- 桌面窗口不拥有 Runtime；关闭窗口后，Growth、Study、子 Agent 和图片任务仍可运行。
- Runtime 提供持久队列、租约、心跳、幂等、断网恢复、崩溃恢复、预算和系统通知。
- 每个 Run 都能查询当前状态、最后活动时间、等待对象和错误类别。
- Provider、网络、协议、工具、权限、持久化和程序错误分别投影。
- 检测卡死、孤儿任务、未配对工具调用、事件流断裂和失去所有权的工作进程。
- Windows 必须原生支持中文路径、PowerShell、进程树取消、后台 sidecar 和干净退出。

## 19. Runtime 所有权边界

CreatX 不应再次深度修改一个上游产品，使其会话、UI、项目文件和领域逻辑纠缠在一起。建议边界为：

```text
CreatX Desktop / Future Web / Future Mobile
  对话、编辑器、Artifact 工作台、任务进度、用户决策
                    |
                    | CreatX Event Protocol
                    v
CreatX Runtime Gateway
  Run 状态、事件日志、任务队列、文件锁、图片队列、版本与审计
                    |
                    | Replaceable Harness Adapter
                    v
Upstream Agent Harness
  模型循环、Provider 调用、工具协议、上下文压缩、子 Agent
```

### 19.1 上游 Harness 负责

- Provider 调用和流式模型循环；
- Tool Loop（工具循环）；
- 工具审批和基础沙箱；
- 上下文压缩；
- 子 Agent 执行；
- 可嵌入的 Headless（无界面运行）接口。

### 19.2 CreatX 负责

- 项目、真实文件、Artifact 和工作台注册；
- 持久 Run、CreatX 事件协议和稳定错误分类；
- 文件锁、Change Set（变更集）、原子写入、撤回和冲突处理；
- Growth、Study、图片队列和全局任务调度；
- 个人、项目和作品三级风格；
- 会话继承记忆；
- 对话、编辑器、图片、HTML 展示和全部前端设计；
- Provider 凭据安全存储、审计和项目权限。

Renderer（渲染层）不得直接依赖上游 Harness 的私有会话对象或消息格式。所有上游事件必须先进入 CreatX Runtime Gateway，由稳定协议投影给前端。

## 20. Harness 调查结论

详细调查见：

`docs/discussions/2026-07-24-creatx-agent-harness-investigation-report.md`

当前只是公开文档、源码和发布记录初筛，不是最终技术选型。统一 Kernel Lab 尚未运行。

### 20.1 当前实测顺序

1. OpenHands Software Agent SDK + Agent Server。
2. Cline SDK + ClineCore / Hub。
3. Goose Core。
4. 干净上游 OpenCode，仅在前三者失败或出现新的上游证据时进入。

### 20.2 当前判断

- OpenHands 当前最符合 CreatX 的 sidecar、事件、可替换前端和 Windows 打包边界。官方示例覆盖持久会话、运行中插话、取消后继续、分叉、模型切换和子 Agent，但进程强杀后的副作用恢复仍未验证。
- Cline 的 TypeScript 嵌入体验、Hub-Spoke 后台架构和 Provider 支持很适合 CreatX，但 SDK 当前为 `0.0.65`，公开历史较短；变更记录中的长会话 OOM 处理包含把 Node.js 最大堆提高到 8 GB，必须实测资源曲线。
- Goose 的 Rust、SQLite、权限、压缩和子 Agent 基础较强，但完整 Core 的嵌入接口和后台协议不如前两者清晰。
- Codex `app-server` 的会话、事件、取消、分叉和诊断能力非常强，但自定义 Provider 的公开 `wire_api` 目前只有 Responses 路线，违反 CreatX 的多协议硬需求。它保留为可靠性标杆或 OpenAI 专用 Adapter，不作为唯一主内核。
- Claude Agent SDK 能力完整，但围绕 Claude 和 Anthropic 商业条款构建，不具备唯一主内核资格。
- OpenCode 上游提供 Server、SDK、会话、Provider、事件和工具，但旧 NovelX 深度修改线出现过严重会话与资源问题。旧故障不能直接证明干净上游失败，也不能成为继续沿用旧代码的理由。

### 20.3 选型硬门槛

候选必须同时通过：

1. 多 Provider 和多协议；
2. 持久 Session 与 Run；
3. 可重放的结构化事件流；
4. 插话、取消、暂停和恢复；
5. 工具调用配对、权限和副作用恢复；
6. Headless 后台运行与前端完全解耦；
7. Windows 原生运行和干净进程管理；
8. 每个无响应都能定位到明确状态或错误。

任一硬门槛失败，不能用其他能力总分补偿。

## 21. 开发顺序

### 阶段 0：协议与测试驱动

- 冻结 CreatX 最小 Run、Event、Tool、Artifact 和错误词汇。
- 建立 Harness Adapter 接口，不绑定具体候选。
- 编写同一套 Kernel Lab 驱动和故障注入脚本。
- 不做正式 UI，不迁移旧 Growth，不导入 NovelX 状态机。

### 阶段 1：双候选 Kernel Lab

先测试 OpenHands，再用相同测试测试 Cline：

- 多轮对话、工具调用和文件编辑；
- Provider 切换和上下文重新投影；
- steer、queue、cancel、resume；
- UI 断开后后台继续和事件重连；
- 子 Agent 创建、并行和单独停止；
- 上下文压缩后继续；
- 模型流、工具执行和副作用完成后的进程强杀恢复；
- Windows 中文路径、进程树终止、打包和残留进程；
- 两小时内存和句柄曲线。

只有统一测试完成后才能确定最终 Harness。

### 阶段 2：第一条纵向闭环

用胜出的 Harness 完成：

```text
打开真实项目
→ 创建会话
→ 用户提出创作要求
→ AI 流式回复并创建或修改一个真实文件
→ Artifact 工作台即时显示
→ 用户直接修改
→ AI 读取用户修改后继续
→ 用户取消并重新开始
→ 关闭窗口后后台继续
→ 重启软件恢复会话和作品
```

该闭环必须包含真实 Provider、真实文件、真实事件持久化、失败路径和 Windows 打包运行。只有 UI、Mock、Fixture 或单元测试不能称为完成。

### 阶段 3：创作基础设施

- 多工作台注册与切换；
- 文档、图片、资料、风格板和 HTML Artifact；
- 文件锁、Change Set、最新一次撤回与取消撤回；
- 个人、项目和作品三级风格；
- 可编辑生图 Prompt 卡和异步图片队列；
- 子 Agent 公开进度和停止入口；
- 会话继承记忆。

### 阶段 4：Study 与 Growth

- Study 先实现来源读取、搜索、风格总结和可追溯笔记，不做训练或微调；
- Growth 建立在已经可靠的持久 Run、任务队列、恢复、预算和子 Agent 上；
- Growth 不采用固定世界到角色到小说链，而是根据用户目标动态建立任务图；
- 图片任务独立排队，不阻塞文字和其他创作任务完成。

### 阶段 5：交互作品与多端

- AI 生成受隔离的 HTML、CSS 和 JavaScript 互动展示；
- 交互作品通过受控接口读取正式 Artifact；
- Web 和移动端复用 CreatX Event Protocol，不直接连接上游 Harness；
- 桌面端仍是首要完整创作环境，Web 和移动端可以先提供查看、对话和任务控制。

## 22. 新会话恢复入口

新会话继续本项目时，按以下顺序阅读：

1. 本文件，理解 CreatX 产品定义、底层能力和开发顺序。
2. `docs/discussions/2026-07-24-creatx-agent-harness-investigation-report.md`，查看候选证据、分数、风险和 Kernel Lab 任务。
3. `BASELINE.md`，确认旧 NovelX 仅为冻结参考素材。

下一项实际工作应是设计 Kernel Lab 的最小 CreatX 协议和统一验收脚本，然后依次测试 OpenHands 与 Cline。未经新的产品决定，不应先做正式前端、不应恢复旧 NovelX Growth，也不应直接从现有 OpenCode 参考代码继续扩建。

当前仍未决定：

- 最终 Harness；
- CreatX Runtime Gateway 使用的进程语言和 IPC 具体格式；
- Windows sidecar 的安装、升级和守护方式；
- Kernel Lab 的最终资源上限；
- 第一版桌面壳采用 Electron、Tauri 或其他方案。

这些问题必须由统一实测和后续产品决策解决，不能把当前候选排序写成既定架构。
