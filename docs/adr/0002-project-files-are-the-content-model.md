# ADR-0002：项目文件是唯一内容模型

## Status

Accepted

日期：2026-07-25

## Context

早期 CreatX 讨论沿用了 NovelX 和内容管理系统的 Artifact（创作产物）概念，设想为文章、图片和交互作品建立注册记录、固定关系和工作台组合。

后续产品讨论确认，CreatX 面向的艺术项目通常具有干净、直接的文件层级。文章、画作、小说、设定和个人见解本来就是文件；AI 可以通过路径、类型、内容、修改时间和用户对话理解它们。把文件再次注册为 Work（作品）或 Artifact 不会为第一条创作闭环提供必要能力，反而引入文件与数据库身份同步、外部修改一致性、分类误判和额外 UI。

项目可能只有一个创作文件，也可能包含多季小说、大量绘画，或由一个世界观向小说、OC 和漫画延伸。当前没有证据要求用固定关系图表达这些联系。文件夹、文件内容和项目共同记忆已经是更直接的表达。

## Decision

- 第一版 CreatX 不建立 Work 或 Artifact 注册表。
- 项目文件与目录是唯一内容模型和内容身份。
- “作品”保留为面向用户的自然语言，不成为必须持久化的技术类型。
- 文件树展示完整项目；一个或多个工作台只是对同一文件树的视图。
- 工作台可以保存名称、图标、排序、文件类型筛选、目录范围、用户选择、置顶、布局和上次位置。这些是视图设置，不改变文件身份。
- AI 工具、事件和记忆引用真实文件路径及其版本。核心文件事件使用创建、修改、锁定、提交和失败等文件语义，不额外要求 `artifact_created`。
- CreatX 可以保存视图设置、Change Set（变更集）、版本、风格、锁和自身任务状态，但不保存第二份作品内容身份。Cline 会话、Run、工具与执行事件的权威归属由 ADR-0005 决定，不属于本文的数据模型。
- 多文件游戏、网站和交互作品继续使用普通目录。
- 只有在出现明确的发布、导出、打包或跨项目引用需求时，才针对那个具体能力评估 Manifest（清单）或其他元数据。任何新增内容实体都需要新的产品证据和 ADR。

## Consequences

### Positive

- 外部编辑器和 CreatX 始终操作同一份内容，不需要同步 Artifact 记录。
- AI、用户和文件监听器共享相同路径与文件事实，减少状态分叉。
- 第一版数据库、协议、UI 和迁移负担更小。
- 用户不需要学习作品类型、关系图或注册流程即可开始创作。
- 工作台和未来前端可以自由变化，不改变项目内容模型。

### Negative

- 系统不能依赖预先注册的作品类型进行精确查询或统计。
- 文件之间的语义关系主要来自目录、内容和记忆，不具备固定关系图查询能力。
- 发布多文件作品或跨项目组合内容时，未来可能需要增加有明确边界的清单格式。

### Neutral

- UI 仍然可以把文章、画作和其他创作文件称为“作品”。该词不对应数据库实体。
- 参考资料、维护文档和创作文件都是项目文件。不同工作台如何展示它们属于视图与使用场景问题，不改变内容模型。

## Alternatives Considered

- 建立通用 Work/Artifact 注册表：拒绝，因为第一版没有必须依赖它的能力，并会产生双重身份和同步负担。
- 建立固定作品关系图：拒绝，因为艺术项目通常规模较小，关系可由目录、内容和项目记忆理解；预设关系类型会增加用户和维护成本。
- 规定作品必须放入特殊目录：拒绝，因为会改变用户原有文件组织方式，并让外部编辑和旧项目接入变复杂。
