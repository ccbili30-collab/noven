## 1. 这份文档解决什么问题

CreatX 的首要工程风险不是单个 Bug，而是产品理解、架构理由、代码状态和恢复入口只存在于一个超长会话中。那会造成：

- 后续 Agent 必须依赖历史聊天才能继续；
- 新需求与旧决定混在一起，无法判断哪个仍然有效；
- 修复一个局部问题时破坏另一条业务链；
- 代码能运行，但已经偏离用户真正想要的产品；
- Mock（模拟）、Prototype（原型）或局部测试被误认为 Live（真实运行）。

本文件保存跨 Agent、跨会话和跨阶段都必须共享的产品理解。`CONTEXT.md` 保存当前状态和恢复入口；代码与测试保存已经实现的行为；ADR 保存重要决策及其理由；证据文档保存真实验收结果。

任何 Agent 都不得把本文件当成静态愿景文案。产品理解发生已接受的变化时，本文件必须在同一可提交批次更新。

## 2. 产品本质

CreatX 是通用的 AI 原生艺术创作工作台，不是只服务小说的 NovelX，也不是把一个聊天框套在代码编辑器或文件浏览器上。

其执行本质仍然是一个完整 Coding Agent（编码智能体）：继承成熟 Harness（智能体运行框架）的会话、模型循环、工具调用、工作区、权限、上下文、取消、历史和继续能力；CreatX 在外部提供面向艺术创作的可见工作台，并通过内置创作工具、Prompt（提示词）、Skill（技能）、上下文和模型路由使 Agent 为创作服务。CreatX 可以保存 Growth Goal、工作台和图片任务等产品事实，但不能复制 Cline 的消息、Run 或工具事实形成平行执行内核。

CreatX 不通过隐藏能力或伪造创作进度来降低 Coding 感。真实工具、文件、命令、模型和图片事件始终可见，默认以创作语言概括并允许展开原始详情。工作台负责更适合创作的投影，不成为第二份运行事实。

计划、审批、协作和自由四档不进入第一版。当前产品只提供“审批 / 自由”直接切换，并让新项目会话默认自由；审批模式逐次确认副作用，自由模式自动批准所有已启用的 Cline Act 工具。项目根目录只是默认工作上下文，不是操作系统沙箱，两种模式下 Cline 文件工具或 Shell（命令行工具）都属于全机信任边界。生产 Runtime、持久配置与 Main/Preload IPC 已实现，Renderer 可见控件和真实 Provider 自由工具验收尚未完成。

一般 Coding Agent 已有成熟行为的部分默认遵循固定 Cline，不在 CreatX 中重新发明。产品与架构讨论只冻结创作工作台、创作工具、图片、个人关系记忆、Growth、Study 等确实需要不同用户结果的边界；其余执行细节通过 Cline Kernel Lab 实测和适配。

用户在 CreatX 中长期建立文学风格、美术风格和个人审美，并创作世界观、人物、小说、诗歌、插画、封面、风格板和交互作品。

核心交互是：

> 用户表达，AI 创作；用户直接修改，AI 重新理解正式作品并继续创作。

CreatX 首先必须成为稳定、可理解、可接管、可恢复的 IDE 式 Agent（智能体）工作台，然后才承载 Growth、Study、生图和更多艺术领域。

## 3. 用户最重视的体验

理解力是 CreatX 的首要质量。这里的理解力包括：

- AI 理解用户当前表达、长期审美、项目目标和正式作品；
- 软件清楚区分用户决定、正式内容、Agent 推测、过期信息和未完成事项；
- 用户直接修改作品后，AI 读取真实文件并基于新内容继续，而不是依赖旧聊天想象文件状态；
- 系统明确展示运行、等待、失败、取消、恢复和结果未知，不能用“模型没反应”掩盖状态丢失；
- 新会话、软件重启和新 Agent 都能从项目事实恢复，而不是依赖一个无限增长的聊天上下文。

用户不需要理解 Rust、SQL、状态机、持久化、并发、进程所有权或数据库迁移。技术 Agent 负责这些实现，并将需要用户决定的内容翻译成产品行为、限制和取舍。

## 4. 内容与数据真相

- 真实项目文件和目录是唯一内容模型。第一版不建立 Work（作品）或 Artifact（创作产物）注册表。
- “作品”是用户对文章、画作、小说、设定、个人见解和其他创作文件的自然称呼，不是必须在数据库注册的技术类型。
- 文件树展示完整项目；工作台根据文件类型、目录、用户选择和布局展示同一批真实文件。
- 工作台可以保存名称、排序、筛选、置顶、布局和上次位置，但这些设置不改变文件身份。
- CreatX 永远提供一个覆盖整个项目根目录、固定 ID 为 `builtin:files` 的内置“文件”工作台。它由系统生成、固定排第一且不写 `.creatx`，并以窄幅文件面板和完整文件工作台两种尺寸呈现同一棵真实文件树；两种投影共享真实文件身份，不能成为两套内容来源。
- 普通文件夹只在内置“文件”表面自然展示。用户或 AI 可以通过严格 `.creatx/workbenches/<id>.json` 记录把某个真实文件夹注册为独立策展工作台；注册不移动、不复制文件，也不产生 Work 或 Artifact 身份。V1 提供标题、相对路径和通用文件夹视图，V2 可绑定交互主页，V3 可由 AI 设置只影响 registered workbench 的包含/排除可见范围；`autoIncludeNewFiles` 默认开启，关闭时冻结当刻匹配文件清单。内置“文件”始终保留普通文件兜底。文件夹路径是注册身份，显示标题可以不同并可由用户通过 AI 显式纠正；改名不改变工作台 ID、文件夹或真实内容。
- 一个注册文件夹最多对应一棵工作台，该工作台可以包含多个页面、视图和内容槽位。父注册覆盖子树；子文件夹只有需要独立工作台时才单独注册。
- AI 通过文件路径、类型、内容、修改时间和文件事件理解项目，不需要 `is_artifact` 或作品关系图。
- 多文件游戏、交互作品和其他组合内容仍然是普通目录。只有出现明确的导出、发布或打包需求时，才为该能力单独决定是否需要 Manifest（清单）。
- 用户可以使用外部程序修改文件，CreatX 需要监听并重新投影。
- Cline 原生持久化保存会话消息、Agent Run（执行轮次）、工具调用与执行结果。CreatX 只保存项目、工作台、图片和用户设置等自身产品数据，以及把 Cline 会话关联到 CreatX 项目的必要标识；第一条骨架不建立第二套消息库、Run 数据库、持久事件日志或持久 UI Projection（界面投影）缓存。
- Provider（模型服务）凭据、个人全局设置和后台总调度属于用户级数据，不能进入项目目录。
- Renderer（渲染层）不能成为会话、任务或文件状态的事实来源。

## 5. 基础创作闭环

第一条真实纵向闭环是：

```text
打开真实项目文件夹
→ 创建或继续会话
→ AI 搜索、读取并理解项目
→ 流式回复和展示工具活动
→ 创建或修改一个真实文件
→ 当前工作台立即显示同一文件
→ 用户直接修改
→ AI 读取用户修改后继续
→ 用户继续编辑并让 AI 重新读取
```

第一版这条链必须包含真实 Electron Renderer（渲染层）、真实 Provider、真实工具结果和真实文件，不能只用后端探针、Fixture 或 Demo（演示）。重启后必须能读取已经保存的会话历史和项目文件，并允许用户发送新的“继续”回合；退出或崩溃时活动 Run 停止，不自动重放在途工具。后台继续、活动 Run 精确续接和严格一次副作用恢复不属于这条骨架，真实使用证明必要后再增强。

## 6. 个人 AI、会话与记忆整理状态

关于跨项目个人 AI、个人长期记忆、项目记忆、跨项目蒸馏、新个人会话继承和从个人会话进入项目的讨论，已经完整捕获在 `../discussions/2026-07-25-personal-ai-session-memory-discovery.md`。

该讨论包含用户对早期“唯一主会话”解释的纠正，并明确新增了“新个人会话可选择旧会话作为来源，由来源会话压缩出默认隐藏的继承记忆”。它还区分了新个人会话继承与当前个人会话进入项目两种流程。

个人长期记忆的未来方向仍是有限文字画像加轻量复盘，而不是细粒度知识库；但长期记忆对短期用户不构成第一版价值门槛，当前整体延期。第一版依赖当前会话、真实项目文件和 Harness 自带压缩，不让画像、跨项目蒸馏或后台复盘阻塞创作能力。

会话相关产品语义已经首轮提升到 `../capabilities/session/`：`product-spec.md` 使用稳定规则编号区分个人会话、项目会话、隐藏压缩继承、完整复制转移和侧聊；`acceptance.md` 定义用户可观察的成功、失败、取消、恢复和幂等场景；`plan.md` 给出依赖顺序和批次边界。

该提升不表示压缩继承、完整复制转移、侧聊及其数据库 Schema（数据合同）或 Runtime 已经接受或实现；`../adr/0003-main-session-forks-into-project.md` 继续是待复核架构草案。基础项目会话和 Workspace UI（工作台界面）已经形成 Live；审批/自由两档已完成 Runtime 与 IPC 接线，Dynamic Growth 仍未形成 Live。个人 AI、长期记忆、项目记忆、跨项目蒸馏和四档权限仍待后续。

## 7. 产品能力方向

当前产品方向包括：

- 动态注册和切换的创作工作台，而不是固定六个 NovelX 页面；
- 右侧任务面板投影 Cline 会话 Run（执行轮次）、Growth Goal 和 CreatX 图片队列，不成为第二套 Cline 执行事实；未来 Automation（自动任务）或子 Agent 只有真实排期后再进入；
- 核心 Prompt 保持精简，小说、世界观、绘画、资料研究和工作台操作等创作能力通过按需加载的内置 Skill 与受验证工具提供；工作台 Skill 必须包含清晰的 Agent 操作教程，但权限、路径、注册格式和真实文件边界由工具合同与 Runtime 强制；
- 工作台协助采用三层合同：每个项目会话的基础 Prompt 只保存文件权威和注册不变量，`register_workbench` 工具说明保存调用前提与幂等语义，小说等领域结构只在对应 Skill 中按需加载。CreatX 内置 Skill 安装到应用数据目录并使用 Cline 原生 `skills` 工具，不写入项目或全局 Cline 配置；普通 Skill 沿用 Session 的审批或自由模式，Skill 不能自行提升权限；
- 项目界面把固定工具与工作台标签分开：最右工作台导航的系统“项目首页”固定第一，内置“文件”固定第二且继续作为不可移除的真实文件兜底，后续项来自 `.creatx` 注册。点击工作台标签从右侧展开，再次点击缩回，主聊天保持可见。项目首页方向已接受但尚未实现；侧聊入口继续隐藏，在真实会话语义实现前不能进入生产入口。
- 文档、图片、资料、风格板、图谱、时间线和隔离交互展示；
- 个人艺术库是一个全局本机资料能力，不是专属 AI 或专属 Chat。任何普通个人/项目会话都可调用同一组应用级工具完成公开图片采集、视觉识读、统一候审、人工批准/驳回、分类移动和分类风格词导出；正式入库必须经过人类批准，分类导出只对三组作品关键词做确定性去重，不调用模型；
- 风格采用真实文件与有限画像：个人审美进入用户画像，项目风格进入项目画像和可见 `style.md`，局部作品风格使用对应目录中的普通说明文件与参考图片；工作台可组织风格板，但不建立作品级风格注册表；
- 一个用户主要面对的主创 Agent，以及可见、可停止、有明确权限的子 Agent；
- 文本模型和图片模型分离配置，生图拥有独立 Prompt、队列和失败状态；
- 图片 Provider 成功返回的全部候选立即保存为项目真实文件；工作台的主图或封面选择只改变视图绑定，未选图片不被自动丢弃；
- 完整 Live 运行通过既有质量门禁后必须进入正式产品档案：真实项目文件、Owner/Worker 会话、Growth 历史、图片任务和最终回复分别进入原权威 Store，不能只留在隔离测试目录；归档不复制密钥，未完成的付费图片任务不会自动续跑；
- 面向用户分享的诺文项目包与内部 Live Archive 严格分离。`.np` 使用标准 ZIP、双身份、确定性完整性校验和新目录暂存提交；真实文件是内容权威，只有用户标记的会话能以净化只读案例进入包，导入历史不成为 Cline 会话、指令、权限或个人记忆。继续创作必须从可审阅说明创建新的普通项目会话；V1 不做签名、合并、自动 Provider 调用或 Profile/数据库复制；
- `/study` 是同一个 Coding Agent 的内置研究 Skill，负责获取、阅读和整理资料，不建立独立页面、Runtime 或专用状态机，也不训练或微调模型；
- `/growth` 是显式启动的持久 Goal 与目标驱动 Skill：CreatX 以滚动规划串行编排多个有界 Cline Run，Cline 仍独占每个 Run 的执行事实；Growth 可注册工作台、组合 Study/地图/因果并向持久单 Worker 图片队列提交任务。第一版不引入子 Agent、并行阶段、固定 NovelX 流水线或关闭窗口后的后台继续；
- `/growth_world_pro` 使用四个可恢复产品阶段：路线、资料与世界方向；十二层骨架；全世界蓝图；自由物化。审阅与冻结属于第三阶段收尾；create/continue/reconcile 只是恢复入口。文类与文风是建议，正文先自由完成，再从最终正文抽取 `source / derived / created` 事实与实际关系。普通语义资料缺口不阻塞 Writer，公开正文内部标签、篇内矛盾、锁定事实冲突和技术身份错误继续失败关闭。Growth 的首要成功标准是一句话启动后由一个 Owner 带领有界 Worker 跑完四阶段、留下真实文件，并在原对话形成用户可理解的正式回复；事实完整性、关系精度与极端恢复精度可以为主链可运行性和文本表现让步，但普通聊天误触发、双主任务冲撞、明显重复或覆盖、伪成功、软件被错误拖死仍不可接受。该优先级纠正记录于 `../discussions/2026-08-05-growth-main-path-priority.md`；
- `/draw-map` 是生成“视觉地图 + 可选择区域”的编排 Skill，不绑定单一算法：既可从图片模型生成的艺术地图与对齐变体提取热区，也可先用泰森网格规划和标记区域，再通过图生图美化；两条路线投影为同一种可选择地图工作台；
- `/causality` 是从当前项目内容推导并展示可选择因果关系网的内置 Skill，可由用户直接调用或供 `/growth` 检查自洽性；第一版不做模拟器和图编辑器，且必须区分真实因果与文件引用、目录包含或普通关联；
- `/living` 第一版是强制视角的角色扮演 Skill：普通 `/living 天空` 进入自由视角，`/living @天空` 可参考项目内容。Living 不再切换工具集或建立零工具 Runtime，工具权限完全沿用当前普通会话且角色身份不产生额外授权；`/unliving` 返回旅鸽；
- 受隔离的 HTML、CSS 和 JavaScript 交互作品；
- 交互作品是普通项目文件，工作台预览默认离线且只能读取作品目录，不继承会话工具权限、终端、凭据或 Electron 原生 API；构建与发布回到普通 Coding Agent 权限链；
- 多 Provider 和多协议，不允许把 OpenAI-compatible 当成所有 Provider 的同义词。

这些是产品方向，不代表已经实现，也不代表应该同时进入第一阶段。

## 8. 当前开发方法共识

采用 Specification-First（规格优先）和 Repository-as-Memory（仓库即记忆）开发。

- 先讨论并冻结难以修改的产品语义、所有权、协议和失败边界；
- 用 Web 原型把模糊体验变成可操作界面，但明确区分 Prototype 与 Live；
- 在主布局形成后加入薄 Electron 壳；托盘、通知、后台运行和复杂进程恢复按风险延期，不阻塞第一版创作体验；
- 在广泛增加功能前完成一条真实 Walking Skeleton（可运行骨架）；
- 每次只开发一个有明确目标、非目标、验收和停止条件的冻结批次；
- Cline 是唯一 Harness；Cline 拥有模型循环、会话、工具、上下文和自身 SQLite，CreatX 不复制这些事实；
- 桌面产品保持 Electron、Renderer、Cline Adapter 与 CreatX 产品能力的明确所有权边界，Renderer 只通过稳定 CreatX 合同访问命令、查询和事件；
- Rust 不再是第一版 Agent Runtime 的必选前置，只在后续真实原生能力需要时按明确所有权引入；
- 一条需要隔离或真实并行的实现批次才对应一个 Worktree，第一条真实骨架先在单一集成批次完成；
- 第一条真实骨架只证明真实 Electron 前端、Cline/Provider、原生审批、一个真实工具、项目文件、同一文件的工作台投影、取消以及重启后读取已保存历史并继续；长期记忆、四档权限、特殊会话、后台继续、活动 Run 精确续接和严格一次副作用恢复不作为前置条件；
- 批次中出现的新想法先记录，除非它使当前产品语义或架构失效，否则不立即扩大范围；
- 每个可提交批次更新代码、测试、文档、证据、已知限制和恢复入口。

讨论越多不会自动提高质量。只有被核对、定级并写入仓库的结论才是项目记忆。

## 9. AI 可维护性要求

- 一个业务规则只能有一个权威实现。
- 模块按完整业务能力组织，不按模糊的 `utils`、`manager` 或技术分层无限拆散。
- 接口只放在真实所有权或可替换边界，不为每个具体实现制造抽象层。
- 跨语言协议只有一个权威来源，Rust、TypeScript 和 Python 类型通过生成或稳定 Schema（数据合同）保持一致。
- 数据库只有一个声明的写入所有者。
- 测试是可执行规格，覆盖成功、失败关闭、幂等、取消、恢复、越权和结果未知。
- 修改一个能力前必须能定位产品意图、权威代码、公开合同、持久数据、测试和用户可见失败行为。
- 如果新 Agent 必须阅读历史聊天才能安全修改，说明上一批维护闭环没有完成。

## 10. 工作区与检查点规则

- `D:\CodexW\Creatx\creat1` 永远保存最新、最深、完整集成的前沿开发头。
- 稳定检查点、参考源码、实验和隔离 worktree 放在 `D:\CodexW\Creatx` 下的英文功能目录中。
- 目录使用 `kebab-case`，例如 `runtime-baseline`、`electron-shell`、`openhands-lab` 或 `novelx-reference`。
- 兄弟目录默认不是项目权威，也不能成为 `creat1` 的运行时相对路径依赖。
- 稳定成果通过 Git 分支、worktree、带来源提交的导出或明确提取合同保存。
- 外部结果返回主线时必须经过审查并进入 `creat1` 的版本历史。

## 11. 当前已接受与尚未决定

已经接受：

- CreatX 是通用 AI 艺术创作工作台，NovelX 只作为历史参考和未来领域模板。
- 真实文件是内容真相，桌面界面与后台 Runtime 分离。
- 第一版没有 Work/Artifact 注册表、固定作品关系图或作品类型体系；项目文件与目录是内容模型，工作台只是文件视图。
- 个人 AI、会话、多层记忆与创作 Skill 的详细语义已完成发现记录；Session（会话）与 Creative Skills 已建立稳定规则编号和验收矩阵，其余能力仍待逐项提升。
- `creat1` 是唯一前沿集成主线，仓库而非长会话是持久事实来源。
- 采用规格优先、Web 产品探索、早期 Electron 壳、真实可运行骨架和冻结批次开发。
- 产品基线和架构基线通过审查前，不写生产功能代码；只进行讨论、仓库文档、证据调查和明确可丢弃的 Web 原型。
- 技术实现必须优先服务跨 Agent 理解、局部修改、失败诊断和可恢复维护。
- Cline 是唯一 Harness，只有 Cline Adapter 可以接触其私有类型；Cline 执行事实与 CreatX 产品事实分别只有一个写入权威。见 `../adr/0005-cline-is-the-sole-agent-harness.md`。
- 灵感库只保留“启发 / 幻想”两个用户可见库：问题句进入启发，陈述式异世界、世界观和其他点子进入幻想；科幻、历史、穿越等降为搜索标签。第一版热度只来自本机喜欢与收藏，不伪造公共社区数据。

当前已接受的实验默认：

- TypeScript/React 承载 Web 与 Electron 共用 Renderer；
- 独立 Web 前端工作线只通过稳定 CreatX 合同接入，不读取 Cline 私有事件；
- Cline Local Backend 已从 Electron Main Process（主进程）迁入受监督 Utility Process（工具子进程）。正式 19 MB 图片历史证明旧拓扑会把 Cline 历史内存和垃圾回收压力带入窗口主进程；当前稳定 CreatX 命令、事件、工具、审批和取消合同保持不变。子进程崩溃时窗口继续响应并失败关闭，不自动重放结果未知的副作用。证据见 `../baseline/creatx-cline-runtime-isolation-2026-08-09.md`。

尚未决定：

- CreatX 产品数据的最小 Schema、迁移库和协议生成工具；
- Electron 与 Cline 的安装、升级及未来后台守护方式；
- 现有 NovelX/OpenCode 参考源码迁移到哪个英文功能目录；
- 完整产品界面的最终视觉系统；第一条骨架的信息结构已经收窄为真实主会话、审批、文件与预览。

不得把“当前方向”写成“已经选定”，也不得因为已有实验投入跳过真实验证。
